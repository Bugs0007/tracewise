# DSA track plan: NeetCode 150

_If a session ends partway: read this file, then `DSA_PROGRESS.md`, and resume at the first unchecked problem._

Goal: a hands-on 150-problem track grouped by topic. Every problem has an original explanation, a Python solution, and a step-through visualization that is generated by running the algorithm (never hand-drawn frames).

## File layout

```
src/dsa/
  types.ts                  ProblemMeta, ProblemContent, TopicContent, PatternId, ...
  catalog.ts                eager and tiny: 18 topics + 150 problem metas (slug, title, difficulty, tags, links)
  patterns.ts               pattern taxonomy used by "Spot the pattern" and checklists
  progress.ts               selectors and actions over the save (solved / review / counts)
  viz/
    prims.ts                primitive builders (array+window, hashmap, set, stack, queue, linked list, tree, trie,
                            heap, graph, grid, dp table, intervals, recursion tree, bits)
    trace.ts                TraceRecorder: Recorder + authored predict checkpoints; makeTrace helpers
  problems/<topic>/<slug>.ts           content + trace generator (lazy, one chunk per problem)
  problems/<topic>/<slug>.py           the Python solution, with #@anchor comments (single source of truth)
  problems/<topic>/<slug>.cases.json   test cases (single source for the browser runner, pytest and the trace test)
  problems/<topic>/<slug>.harness.py   optional: adapter for design/linked-list/tree problems
  topics/<topic>.ts         lazy topic content: intro, template, recognise checklist, boss fight
  pages/DsaIndexPage.tsx, TopicPage.tsx, ProblemPage.tsx, GalleryPage.tsx, dsa.css
tests/dsa/
  conftest.py               loads solution + cases + harness, comparison modes (same as src/runner/compare.ts)
  test_<topic>.py           one pytest file per topic
  oracle.py                 runs every Python solution on its case inputs and prints JSON (used by the TS test)
src/dsa/dsa.test.ts         catalog integrity, frame well-formedness, trace result == Python result
```

Single source of truth per problem: the `.py` holds the solution (with `#@anchor` markers that the visualizer uses to highlight the executing line), and the `.cases.json` holds the tests. The browser, pytest and the TS trace test all read those two files, so the three can't drift apart.

## Data schema

```ts
interface ProblemMeta {            // catalog.ts, eager
  id: string;                      // LeetCode slug, e.g. 'two-sum'. Unique across the 150.
  n: number;                       // 1..150 NeetCode order
  title: string;
  topic: TopicId;
  difficulty: 'Easy' | 'Medium' | 'Hard';
  patterns: PatternId[];           // tags
  leetcode: string;                // URL
  free?: { label: string; url: string };   // premium problems: a free equivalent
}

interface ProblemContent {         // problems/<topic>/<slug>.ts, lazy
  summary: string;                 // own words, 2-3 sentences
  example: { input: string; output: string; note?: string };   // our own example, not copied
  pattern: { answer: PatternId; options: PatternId[]; why: string };
  hints: string[];                 // 2-3, progressive
  explanation: {
    insight: string;               // 1-2 lines
    brute: string; optimal: string;                // one line each
    walkthrough: string[];         // expandable
    edgeCases: string[];           // expandable
    whyItWorks: string[];          // expandable
  };
  complexity: { time: { big: string; why: string }; space: { big: string; why: string } };
  solution: string;                // from the .py (with anchors)
  task: { fnName; signature; tests; compare?; harness?; adapter? };
  viz: VizDef;                     // trace generator; viz.code is the solution
}
```

The trace generator is `viz.run(input)`: it executes the algorithm and records frames through `TraceRecorder` (state snapshot as panels, highlighted elements as tones/pointers, a one-line caption, the active solution line via an anchor, and the variables table). `viz.reference(input)` is an independent brute-force implementation.

### Predict-the-next-step checkpoints

`Frame.predict?: { question, options, answer, explain? }` is optional. The generator calls `r.predict(kind, question, options, answerIndex)` right before the step whose outcome is being predicted. Only the first occurrence of each `kind` is kept and at most 3 per trace, so any input gets 2-3 checkpoints at the key moments (a first miss, the first hit, the decisive step). The answer is computed from the live algorithm state. The Player pauses at that frame when Predict mode is on, asks the question, then plays the step. The old caption-based quiz is still used by the existing units.

### Progress

`SaveData` gets one new field and the schema goes 1 to 2 (so an older client can't overwrite a newer cloud copy):

```ts
dsa: {
  problems: Record<slug, { status?: 'solved' | 'review'; at?: string; pattern?: boolean; hints: number;
                           predictRight: number; predictTotal: number; typed?: boolean; revealed?: boolean }>;
  bosses: Record<topic, { quizBest?: number; solvedAt?: string }>;
}
```

- `status` is set by "Mark solved" / "Needs review". "Needs review" also schedules a Leitner item (`scheduleReview`, key `dsa:<slug>`, kind `problem`). It shows up in the existing review list as a link to the problem.
- Passing the in-browser tests marks `typed`. Solving awards XP through `awardXp` (so streak and daily goal count). Finishing a topic's problems awards a badge.
- `mergeSaves` gets a `mergeDsa` join: statuses take the latest `at`, counters take max, flags OR.
- One store, one localStorage key, one sync path.

## Visualizer primitives (`src/dsa/viz/prims.ts`)

Each primitive is a pure builder that returns existing `Panel` objects, so the Player and its styling are shared:

| Primitive | Backed by |
|---|---|
| `arrayView` (array / string with pointers and window brackets) | `ArrayPanel` (`pointers`, `range`) |
| `hashMapView`, `hashSetView` | `KVPanel`, `ListPanel` |
| `stackView`, `queueView` (also deque) | `ListPanel` |
| `linkedListView` (pointer tags, rewiring via dashed edges) | `linkedListPanel` |
| `treeView` (binary tree) | `binaryTreePanel` |
| `trieView` | `nTreePanel` |
| `heapView` (tree + array view together) | `binaryTreePanel` + `ArrayPanel` |
| `graphView` (visited, BFS/DFS frontier) | `graphPanel` + `ListPanel` frontier |
| `gridView` (matrix, board, island grids) | `GridPanel` |
| `dpTable1D`, `dpTable2D` (cell dependency arrows) | `GridPanel.arrows` |
| `intervalsView` (number line) | new `IntervalsPanel` (type + renderer) |
| `recursionTree` | `nTreePanel` |
| `bitsView` | `ArrayPanel` with bit index labels |

Only `IntervalsPanel` is a new engine panel type (nothing existing draws a number line). Two small engine options were added along the way: `ArrayPanel.wrap` (long strings wrap instead of scrolling sideways) and `VizDef.validate` (readability limits on edited input that must not apply to test inputs). `dsa.test.ts` checks every primitive for well-formed output, and `#/dsa/gallery` renders each in a few states for visual review (light, dark, phone).

## Problem page (top to bottom)

1. Summary (own words), one small example, LeetCode link (plus a free link for premium problems).
2. **Spot the pattern**: pick 1 of 3-4 patterns, with feedback. Hints, explanation and visualizer stay locked until answered (a visible "skip" avoids dead ends).
3. Hints, one at a time.
4. Explanation: insight + brute vs optimal, then expandable walkthrough / edge cases / why it works.
5. Visualizer (Player) with Predict mode on by default, editable input, solution panel with the live line.
6. **Type it yourself**: `TaskRunner` (Pyodide, already in the repo, so no new dependency). The reference solution is hidden behind a Reveal button.
7. Complexity with one-line justification each.
8. Mark solved / Needs review.

## Topic page

Intro (pattern in a few lines), reusable Python template, "how to recognise it" checklist, problem list with difficulty and progress, boss fight (timed mixed pattern-recognition quiz, then one problem with hints, visualizer and reveal turned off).

## Correctness gates (per topic, before ticking a problem)

1. `python -m pytest tests/dsa/test_<topic>.py`: each solution passes at least 5 cases including edge cases (empty, single, duplicates, negatives, large where relevant).
2. `npm run test:dsa` (vitest, then pytest): the trace result equals the result of actually running the Python solution (via `oracle.py`) on every case input; frames are well formed; 2 to 3 checkpoints exist; viz result equals its reference.
3. `npm run lint && npm run typecheck && npm test && npm run build` pass.

CI installs pytest and runs `npm run test:py` (the Python setup step was already there).

## Known issue outside this track

At 390px wide every page of the app (home and the old unit pages too) scrolls sideways by about 95px because of the top bar's Google "Sign in" chip. The track's e2e test measures the content area instead. Fixing the top bar is a separate change.

## Decisions worth flagging

- Test cases live in `.cases.json`, not inline in the pytest file, so the browser's "Type it yourself" runner and pytest use identical cases. The pytest file per topic still lists the topic's problems and adds hand-written property tests (brute-force comparisons) where useful.
- Premium problems link to a free equivalent. Each URL is checked before it is committed.
- Content is original: summaries, examples and constraints are paraphrased, and no statements are copied from LeetCode.
- No personal names or personal projects appear in any content. The repo is public.
